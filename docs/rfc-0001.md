# RFC-0001: Doability Intelligence v0.1

Status: Draft  
Type: Specification  
Scope: Pre-decision capability and limitation assessment

## Abstract

Doability Intelligence (DI) is a pre-decision layer for mapping what can and cannot be done before decisions become commitments.

DI clarifies capabilities, limitations, constraints, unknowns, risks, and feasible action paths before a system promises, plans, executes, or records a decision.

DI does not decide.
DI does not execute.
DI does not record final decisions.

DI exists to prevent systems from treating requests as immediately actionable when capability, permission, context, safety, reversibility, or human approval boundaries remain unresolved.

## Core Thesis

> DI maps what can and cannot be done before decisions become commitments.

## Principle

> Do not promise action until limits are understood.

## Motivation

Modern intelligent systems often respond to a request as if the next correct step is action.

This creates several failure modes:

- technical capability is mistaken for permission,
- unknown constraints are treated as absent constraints,
- missing context is silently filled by assumption,
- risky or irreversible actions are framed as ordinary tasks,
- human approval boundaries are bypassed,
- feasibility assessment collapses into commitment.

DI introduces an explicit layer between intent clarification and decision commitment.

Its purpose is to make limits visible before a system crosses into decision, execution, or responsibility.

## Scope

DI covers the pre-decision assessment of:

- capabilities,
- limitations,
- constraints,
- unknowns,
- risks,
- feasible actions,
- blocked actions,
- human-review requirements,
- recommended next steps.

DI answers:

> Under what conditions, constraints, and risks could this action be validly attempted?

## Non-Goals

DI is not:

- an execution engine,
- a decision log,
- a policy engine,
- a task manager,
- a productivity system,
- a SaaS platform,
- a replacement for human judgment.

DI does not decide what must be done.
DI clarifies what can, cannot, should not, or cannot yet be done.

## Core Terminology

| Term | Meaning |
|---|---|
| Request | The raw instruction, signal, or demand received by the system. |
| Intent | The clarified meaning behind the request. |
| Capability | A function the system can technically perform. |
| Limitation | A known condition that prevents, weakens, blocks, or constrains action. |
| Constraint | A rule, boundary, policy, condition, or requirement that affects feasibility. |
| Unknown | Missing information that affects whether action is valid. |
| Feasible Action | An action path that can be attempted under known conditions. |
| Blocked Action | An action path that must not be attempted under current conditions. |
| Human Review | A required human check before action becomes valid. |
| Commitment | The transition from assessment into decision, promise, plan, execution, or record. |

## Relationship to DIF and DRP

DI is the middle layer between intent clarification and decision commitment.

```text
DIF → clarify intent
DI  → clarify limits
DRP → commit decision
```

Layer roles:

```text
DIF — do not act until intent is understood.
DI  — do not promise action until limits are understood.
DRP — do not forget why a decision was made.
```

DIF clarifies what the human actually means.

DI clarifies what can and cannot be done under current constraints.

DRP records the committed decision, rationale, responsibility, and causal links.

DI ends when a decision is ready to be recorded.
DRP begins when a decision becomes a commitment.

## DI Lifecycle

A DI assessment follows a minimal lifecycle:

```text
1. Receive request
2. Identify or import clarified intent
3. Map capabilities
4. Map limitations
5. Map constraints
6. Identify unknowns
7. Classify feasible and blocked actions
8. Recommend next step
9. Stop before commitment
```

DI should not silently move from step 8 into execution or decision recording.

A separate decision boundary is required before DRP or execution begins.

## Assessment States

DI uses the following action-path states:

| State | Meaning |
|---|---|
| allowed | The action is feasible under current known conditions. |
| allowed_with_constraints | The action is feasible only if listed constraints are respected. |
| blocked | The action must not be attempted under current conditions. |
| unknown | Feasibility cannot be determined from available information. |
| requires_human_review | Human approval or judgment is required before commitment. |

These states describe feasibility.
They do not authorize execution by themselves.

## Minimal DI Assessment Model

A minimal DI assessment may contain:

```json
{
  "check_id": "check-example-001",
  "request": "Help the user resolve an account issue and send the result to the support system.",
  "inferred_intent": "Prepare a safe support resolution path without unauthorized account actions.",
  "capabilities": [
    "Summarize user-provided issue details.",
    "Draft a support note for human review."
  ],
  "limitations": [
    "User identity is not verified.",
    "Support-system write access is unknown."
  ],
  "constraints": [
    "Privacy boundary.",
    "Permission boundary.",
    "Human approval boundary."
  ],
  "feasible_actions": [
    {
      "action": "Prepare a structured support note for human review.",
      "status": "allowed_with_constraints",
      "conditions": [
        "Use only account-safe details.",
        "Do not claim resolution without confirmation."
      ]
    }
  ],
  "blocked_actions": [
    {
      "action": "Change account settings directly.",
      "reason": "Account authority and identity are not verified."
    }
  ],
  "unknowns": [
    "Whether the user is verified.",
    "Whether the support tool is approved."
  ],
  "recommended_next_step": "Prepare a structured support note and request human review."
}
```

## Invariants

DI v0.1 defines the following initial invariants:

1. A system must not treat capability as permission.
2. A system must not treat unknown constraints as absent constraints.
3. A system must not convert feasibility assessment into commitment without an explicit decision boundary.
4. A system must distinguish allowed, constrained, blocked, unknown, and human-review-required action paths.
5. A system must not promise execution when limitations are unresolved.

## Valid and Invalid Commitments

### Valid Commitment Example

A system may commit to:

```text
Prepare a local support note for human review.
```

when:

- no account state is changed,
- no private data is sent to an unapproved system,
- unresolved limitations are explicitly preserved,
- human review remains required before external submission.

### Invalid Commitment Example

A system must not commit to:

```text
Resolve the account issue and submit the result.
```

when:

- identity is not verified,
- support-system write permission is unknown,
- issue category may involve billing, access, or security,
- external submission has not been approved.

The invalid case fails because it turns unresolved feasibility into implied execution.

## Security and Safety Considerations

DI is safety-relevant because pre-decision mistakes can propagate into unsafe commitments.

Key risks include:

- capability overclaiming,
- permission bypass,
- hidden assumptions,
- policy boundary collapse,
- premature execution,
- loss of human review,
- irreversible action without feasibility mapping.

DI reduces these risks by forcing limitations and unknowns to be represented before commitment.

However, DI is not sufficient on its own.

A DI assessment can still be wrong, incomplete, or biased.
For high-impact domains, DI outputs should be reviewed by humans and recorded through a decision protocol such as DRP when a commitment is made.

## Open Questions

- Should DI define a stronger canonical assessment object beyond the current seed schemas?
- Should unknowns have severity levels?
- Should feasibility checks support evidence anchors?
- Should DI integrate directly with DRP records or remain loosely coupled?
- Should CI eventually validate examples as well as fixtures?
- What is the minimal boundary between DI assessment and policy enforcement?

## Status

This RFC is a draft seed specification for DI v0.1.

It defines DI as a narrow pre-decision layer and preserves the boundary:

```text
DI clarifies limits.
DRP records decisions.
Execution is outside DI.
```
